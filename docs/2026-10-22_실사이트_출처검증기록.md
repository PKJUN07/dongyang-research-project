## 저장 반영과 보존 검증

1. SQLite backup API로 실행 중 DB의 일관된 백업을 현재 작업 폴더 output/2026-10-22-before-source-review-verified.db에 생성했다. 라이브 DB의 WAL을 무시한 파일 복사는 하지 않았다.
2. ReprocessDocuments --dry-run으로 ID 1,7,8,14,17의 대상·정책·예상 분류를 확인했다.
3. 같은 명시적 ID에만 --apply를 실행했다. 결과는 OFFICIAL 2, USER 3, 나머지 OTHER 12다. BLOCKED 1, METADATA_ONLY 16, contentText 비어 있음 17건이다.
4. 백업과 원본을 대조한 topic, search_hit 전체, 검색 조건·요청키·시각·건수, 원래 URL·제목·합성 여부, provider_budget의 SHA-256 지문이 모두 동일했다. SQLite integrity_check=ok다.
5. SERPER attempts=2를 유지했다. 작업 1은 PARTIAL/7건/본문 제한 1건, 작업 2는 SUCCEEDED/10건/실패 0건이다. 발행일은 미상(null), 본문 수집 시각도 null이며 분류 확인 시각만 추가했다.

백업·실제 검색 영수증·개인 DB는 배포하거나 Git에 넣지 않는다. 5건의 재검토는 검색을 재실행하거나 요청 키를 바꾸는 방식이 아니다. 기존 본문이 있는 문서는 도구가 덮어쓰기를 거부한다.
